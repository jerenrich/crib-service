# Classifier background failure and fix options

Investigation date: 4 November 2026. The original logging-only update was merged as `7100cb9`. The later recovery/integrity merge preserves those diagnostics and the existing built-in classifier. Dated observations below describe their respective tested builds.

## Subsequent physical validation and combined fix

A separate same-code A/B test on J14 found that adding `processing` to the existing background modes allowed the built-in request to continue in the background and while locked. The reviewed recovery/integrity build later passed **10 minutes 30 seconds of confirmed locked-screen scoring**, with 629 complete windows, exactly one-second cadence, one capture and no failure/gap records. A subsequent readback covered **73 minutes 52 seconds** of uninterrupted scoring through 22:43:33 UTC, including a return to the foreground without a reset. This is device/OS/interval evidence, not a public guarantee of indefinite GPU access, full-night stability or recognition accuracy. See [the A/B and deployment receipts](diagnostics-review.md).

The combined source retains the original safe failure reasons/cause chains, sampled operational failure/recovery records, capture-start reasons, runtime GPU-support query and protected-file probe diagnostics. It adds `processing`, failure backoff independent of microphone gaps, conditional foreground recovery, stale-event protection and robust concurrent CSV export/retention. No continued-processing task, new GPU entitlement, alternate model or change to volume alerts is introduced. The original diagnostic-only build and the physically tested recovery build were different installations; the combined source has its own automated validation.

## Stream stall recovery — 6 November 2026

While microphone buffers continue arriving, the classifier now requires an advancing, valid, input-mapped result within ten seconds of session creation or the last observed progress. The watchdog uses a monotonic clock and accepts quiet/low-confidence results as progress. Duplicate windows do not extend its deadline. A stalled session emits an analysis failure with the fixed reason `result_timeout`, stops, and follows the existing 1/2/4/8/16/30-second retry backoff and conditional foreground recovery. Capture replacement resets the watchdog; Stop and Standby do not run recovery. No timer runs independently of input delivery. The 80% detection threshold, audio-window configuration, alert timing, volume path and shared episode rules are unchanged.

Validation passed **268 shared Swift tests** and **507 iOS simulator unit/integration tests**. The missing-first-result, post-success stall and repeated-window regressions failed against the previous implementation before the fix. Additional coverage verifies timeout boundaries, retry backoff through input gaps, fresh low-confidence progress, lifecycle resets, no recovery without input, safe timeout diagnostics and unchanged volume-alert timing/configuration. No physical-device test or deployment was performed.

### Recovery diagnostic evidence — 6 November 2026

Timeout failures now carry one bounded snapshot: configured timeout, session age and time without progress in monotonic milliseconds; the number of submitted buffers and their total audio duration; and the last advancing result's audio-clock end, or `none` if scoring never began. These fields reach both the CSV `classifier_unavailable` detail and the sampled operational `classifier_failure` record. The operational record also retains the original failure time, capture correlation and retry delay. Numeric milliseconds are capped at one day and counters at one billion; they are diagnostic context, not unbounded histories.

Both exports now share recovery validation. Only an advancing, fresh result from the currently running capture, with an independent input timestamp, confirms recovery. Results from unknown, failed, stopped or replaced captures, stale input, delayed handling, invalid scores and incomplete post-gap windows cannot declare success. The first qualifying score gains `recovery=confirmed` in its existing CSV detail; the operational log emits `classifier_recovered`. Summaries link failed and recovered captures and include first/latest failure times, total failures and restart count. `outage_ms` measures from the first observed failure to recovery, using wall time and explicitly labelled as such; it excludes the watchdog's preceding detection delay. A pending-recovery summary appears in operational exports before success. This bookkeeping is process-local and resets on monitoring stop/pause; an app relaunch is not proof of recovery.

Storage impact is small during normal operation: no new periodic/per-buffer rows, and no extra rows while healthy. Expect roughly **1–2 KiB of additional text per isolated failure/recovery pair** across both exports, depending on populated fields. Equivalent operational failures still sample at 60 seconds even when capture IDs or snapshot counters change; CSV failures retain every attempt. A continuously stalled classifier at the capped 30-second backoff adds approximately **1 MiB/day or less** of diagnostic text; frequent cycles of failing and recovering can add several MiB/day. The existing **10,000-line operational ring**, **42-day/2 GiB CSV cap**, rotation, batching and coverage/loss counters are unchanged. No audio, arbitrary error descriptions or credentials are added. The CSV still may lose its latest batched seconds on abrupt termination; the operational failure record is written immediately, subject to the existing storage-failure reporting.

Validation passed **272 shared Swift tests** and **513 iOS simulator unit/integration tests**. Regressions cover the actual stream's timeout snapshot, bounded counters/payloads, sampling across changing captures and timing values, pending-outage export, current-capture/input-clock validation, retired failures and results, post-gap windows, one recovery annotation per outage, persisted operational evidence and both exports through `AppModel`. Detection thresholds and alert behavior are unchanged. No physical-device test or deployment was performed.

## Recommendation

**Keep Apple's existing built-in `.version1` model and continue longer collection with the verified recovery configuration.** No model replacement or new model training is part of this fix. Earlier system logs confirmed a permission failure during background GPU execution; subsequent physical tests above establish that the updated configuration continued scoring on J14 for the observed intervals.

The runtime `BGTaskScheduler.supportedResources.contains(.gpu)` result remains useful diagnostic context. If the verified configuration later proves unreliable, an advertised GPU capability could justify a bounded, user-started `BGContinuedProcessingTask` experiment with the Background GPU Access entitlement. Task admission, cancellation/expiration and real progress reporting would need handling. This remains an alternative experiment, not a requirement of the current fix or an Apple guarantee of indefinite overnight execution. If J14 does not advertise GPU support, that mechanism cannot provide it on the device. [Supported resources](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/supportedresources), [continued processing](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask), [GPU resource and entitlement](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtaskrequest/resources/gpu).

There is no public compute-unit selection on `SNClassifySoundRequest(classifierIdentifier: .version1)` in the installed SDK. `MLModelConfiguration` applies to a model the app creates; a separately created configuration object cannot configure that built-in request. No supported public way to obtain the built-in classifier as an independently configurable `MLModel` was found. [Apple model configuration](https://developer.apple.com/documentation/coreml/mlmodelconfiguration), [sound request initializers](https://developer.apple.com/documentation/soundanalysis/snclassifysoundrequest).

If the built-in path cannot meet the locked-phone requirement, the fallback is an **existing pretrained model bundled by the app**, not necessarily a model we train. Google's YAMNet through MediaPipe/LiteRT with an explicit CPU delegate is the best first fallback prototype: the original class map includes `Baby cry, infant cry` at index 20, and the official iOS API handles audio preprocessing. This remains an unvalidated candidate. [Model and inputs](https://www.kaggle.com/models/google/yamnet), [upstream class map](https://github.com/tensorflow/models/blob/master/research/audioset/yamnet/yamnet_class_map.csv), [official iOS integration](https://developers.google.com/edge/mediapipe/solutions/audio/audio_classifier/ios).

A self-contained pretrained Core ML conversion loaded with [`.cpuOnly`](https://developer.apple.com/documentation/coreml/mlcomputeunits/cpuonly) is another reuse path, with additional conversion/preprocessing work. In Apple API terminology, a “custom model” means app-supplied; it does not imply training from scratch. A newly trained Create ML classifier is a separate, optional longer-term choice.

## What is confirmed on this device

- J14 is an iPhone 14 Pro running iOS 27.2 in this test. Source `bf25f998346404f9deb84715940fc2716c21fb1e` used Apple's built-in SoundAnalysis `version1` classifier, two-second windows and 50% overlap.
- Monitoring started at 07:39:22 UTC. Classifications were initially produced. The last scored window ended at 07:42:22.377; the app logged background entry at 07:42:22.649 and the first classifier-unavailable record at 07:42:23.412.
- A later live, process-filtered system-log read captured 101 GPU-denial messages, including `Insufficient Permission (to submit GPU work from background)` and `kIOGPUCommandBufferCallbackErrorBackgroundExecutionNotPermitted`, followed by Core ML prediction failure and SoundAnalysis analysis failure. This confirms the GPU permission failure on J14; it is not an inference from another developer's report.
- The ordinary RMS level stream continued and generated a real alert at 07:46:22.372. The Parent recorded receipt, alarm scheduling, alerting and acknowledgement. The classifier is observational and does not control those alerts.
- The original observer discarded the `didFailWithError` error. The existing CSV therefore showed unavailable/restart markers but not the framework error chain.
- There is a separate retry defect: after a failure, the failed-epoch guard skips buffers without advancing `expectedFrame`; a subsequent mismatch is treated as a gap, clears `failedEpoch` and recreates the model. This amplifies a continuing OS restriction into repeated session restarts. A setup-time throw need not follow the same path.

Evidence is retained locally under ignored `.local/classifier-investigation-2026-11-04/diagnosis.json` and `.local/alert-review-2026-11-04-0749/`. A remote process-launch command returned success during diagnosis, but subsequent samples still reported background state; it did not establish a controlled foreground-recovery experiment.

## Options assessed

| Option | Evidence and limits | Decision |
| --- | --- | --- |
| Force Apple's built-in request to CPU | The public request API exposes built-in/custom-model initialization and window/overlap controls, not an `MLModelConfiguration` or compute-unit property. | No supported switch found; avoid private KVC/model extraction. |
| Add the `processing` background-mode checkbox | Forum reports are mixed and the documentation does not promise arbitrary GPU inference. Subsequent same-code A/B and longer J14 observations succeeded with this configuration. | Included in the tested fix; retain the distinction between device evidence and a universal/overnight guarantee. |
| Use `BGContinuedProcessingTask` plus background GPU access | Apple documents user-initiated finite work, device resource checks, a separate entitlement, task submission/admission, progress UI, and expiration/cancellation handling. | Preferred capability-gated experiment for retaining Apple's model; still not a guaranteed indefinite overnight contract. |
| Keep the built-in classifier only when foregrounded | Avoids exercising the observed denied background path, but supplies no classifier observations while the nursery phone is locked. | An honest limited mode, not a solution to continuous background classification. |
| Create ML custom classifier, then `.cpuOnly` | Apple supports custom sound models and configurable Core ML execution. Training data and validation are needed. Some Create ML models use system audio feature extractors, so inspect and test the complete pipeline. | Viable longer-term native route; do not assume a new classification head alone proves independence from the old inference path. |
| YAMNet through MediaPipe/LiteRT, CPU delegate | Original model has 521 classes including baby cry. Google supplies an iOS audio-classifier API; the CPU delegate is explicit and defaulted in its public base-options source. AudioData can load an existing float buffer. | Best pretrained fallback proof of concept if the Apple-model path is unavailable or unreliable; validate power and accuracy. |
| Convert YAMNet to Core ML, `.cpuOnly` | Gives native inference control. An inspected community conversion accepts `[1,96,64]` log-mel patches, not raw audio. Feature extraction and numeric parity would remain our responsibility. | Plausible optimization after the CPU proof of concept; not a drop-in binary replacement. |

Apple documents the GPU task requirements and cancellable, progress-based lifecycle in [Performing long-running tasks](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados) and the [GPU resource option](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtaskrequest/resources/gpu). This is why background-task APIs are not treated as a blanket permission upgrade. See also [background execution modes](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes).

The original [SoundAnalysis background-failure discussion](https://developer.apple.com/forums/thread/765376) includes an Apple engineer's request for a bug report and conflicting user workarounds; it is not an Apple-confirmed universal fix. Our current device evidence establishes that the failure still exists on this tested OS/device combination.

## Concrete implementation path

1. **Contain the restart loop in a separate behavioral fix.** Latch failure for an analysis epoch without treating intentionally skipped buffers as a reason to retry. Permit recovery only at an explicit boundary, such as a real capture reconfiguration, monitoring restart, or deliberate foreground recovery. Keep volume detection independent. Test continuous and discontinuous input after failure and ensure late callbacks cannot revive an old capture. The logging patch records the existing retry behavior; it does not silently change this policy.
2. **Test the existing Apple model before replacing it.** Read the new runtime GPU capability field on J14. If supported, prepare a bounded user-initiated continued-processing task with `.gpu` resources, the required entitlement, task-start/expiration/cancellation diagnostics and genuine progress reporting. Compare the same built-in request in foreground, background and lock, first briefly and then under the overnight requirement. A capability flag alone is not a successful task admission or a successful SoundAnalysis inference. Keep volume detection independent if admission or inference fails.
3. **If necessary, run an observational pretrained CPU prototype before replacing production inference.** Pin the original YAMNet LiteRT model/version/checksum and inspect its metadata/license. Google's model card identifies Apache 2.0 licensing; verify the exact selected LiteRT variation and retain its notices before distribution. Set `baseOptions.delegate = .CPU` explicitly, using the API names of the pinned dependency version. Do not enable a GPU delegate. [CPU delegate source](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/ios/core/sources/MPPBaseOptions.h).
4. **Reuse the current audio tap.** Feed bounded, transient copies of its PCM data to the analysis worker. Use `AudioData.load(buffer:offset:length:)` rather than the sample app's separate microphone recorder. That preserves the existing recording session, volume detector and nursery-playback behavior. Google's [AudioData API](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/ios/audio/core/sources/MPPAudioData.h) permits loading float buffers; its [audio-classifier guide](https://developers.google.com/edge/mediapipe/solutions/audio/audio_classifier) describes resampling, framing and other preprocessing. Verify the actual selected model's sample rate/channel metadata.
5. **Keep observations comparable without pretending they are identical.** Record model ID/version, input sample rate, actual window and hop duration, and the exact baby-cry class mapping. YAMNet's original waveform model uses 16 kHz mono, 0.96-second windows and 0.48-second hops. Read the baby-cry score even when it is low; do not use a top-k filter that silently removes it. These scores are not interchangeable with Apple's `baby_crying` confidence. [Original model card](https://www.kaggle.com/models/google/yamnet), [preprocessing source](https://github.com/tensorflow/models/tree/master/research/audioset/yamnet).
6. **Measure before changing alert decisions.** Exercise foreground, Home/background, lock, unlock, Stop/Standby/Resume, interruption, route change and nursery playback on J14. Verify advancing audio-window timestamps and continuous scores while locked, bounded memory/backlog, no GPU-denial logs, and unchanged RMS alerts. Measure inference latency, CPU, battery/thermal behavior and sample gaps against the existing volume-only baseline. Start with a short locked test, then a 30-minute run and an overnight run. User-labelled quiet, speech, white noise, lullaby and cry examples are needed to evaluate accuracy; model availability alone proves neither accuracy nor overnight reliability.

`.cpuAndNeuralEngine` is a later optimization candidate because it excludes GPU according to [Apple's API contract](https://developer.apple.com/documentation/coreml/mlcomputeunits/cpuandneuralengine). It is not assumed to provide the same background behavior or power results as CPU-only inference without a separate physical-device test.

For the Core ML conversion alternative, the inspected [conversion author's model card](https://huggingface.co/Yehor/YAMNet-CoreML) explicitly requires log-mel features. It would require preprocessing parity tests against the upstream model before use; the native SoundAnalysis wrapper cannot be assumed to supply those features to an arbitrary feature-array model.

## Logging implemented in this change

Both the study CSV and normal diagnostics now retain useful failure context:

| Record | New evidence |
| --- | --- |
| `classifier_unavailable` CSV row | Capture ID when available; `stage=setup|analysis`; fixed reason; up to four allowlisted domain/code causes; truncation marker; app activity when the event is handled. |
| `capture_start` CSV row | `reason=initial|monitoring_restart|audio_gap|after_failure`, plus existing sample-rate/voice-processing context. |
| `classifier_failure` operational row | Same safe failure data and capture correlation. Equivalent failures are sampled for 60 seconds across changing capture IDs; the next emission includes the number suppressed. Stage, error or activity-context changes emit immediately. |
| `classifier_recovered` operational row | First valid score whose observation and audio-window end follow failure, with capture ID/activity context and suppression count. Late delivery of an old window cannot declare recovery. Resets failure sampling so another failure is visible immediately. |
| `run_start` CSV row | On supported iOS versions, the value returned by `BGTaskScheduler.supportedResources.contains(.gpu)`. This is capability evidence, not permission for the current audio-only execution path. |

No raw descriptions, paths, userInfo, audio or credentials are exported. Unknown error domains become `other`. `background_gpu_denied` is emitted only when an allowlisted error chain contains a recognized explicit GPU-denial marker; a generic SoundAnalysis code 2 while backgrounded remains `operation_failed`. If Apple's callback omits the low-level GPU cause, logs cannot reconstruct it. Device system logs may still be needed.

The CSV keeps its existing 19-column schema and bounded storage. Detailed failure rows retain their original event timestamps; `app_active` describes context at handling time and is not an assertion about the exact instant of GPU submission. This change adds diagnostics without changing classifier selection, retry policy, thresholds, pairing, server behavior or alert routing.

| Area | Finding | Result |
| --- | --- | --- |
| Server API | Unexpected errors became a generic 503 with no retained evidence. ## Privacy and retention contract

Server diagnostic rows contain operational timestamps, a random request UUID, fixed operation/stage/outcome labels, numeric status/duration/attempts, phone/watch destination, a Worker release UUID and optional HMAC-SHA256 event reference. The HMAC is namespaced and keyed using the existing server pepper. It does not hash or retain device identity. References identify an event across retries; they are pseudonymous, not anonymous, and must be treated as sensitive operational data.

No diagnostic row contains request or response bodies, arbitrary URLs/paths/query strings, arbitrary headers, IP addresses, device UUIDs, episode/event UUIDs, pairing codes, push tokens, credentials, configuration values, battery readings, crying timestamps/durations, audio/features or raw exception messages/stacks. Unknown routes and APNs reasons map to fixed fallback labels. Incoming correlation IDs are ignored. Diagnostics are accessible through operator D1 access only; there is no diagnostic API endpoint.

The minute cron attempts to delete journal rows older than seven days **before** delivery work. Cleanup failure records `diagnostic_cleanup_failed` when journal writes remain available, and allows alert delivery to continue. An insertion trigger caps the journal at the most recent 10,000 sequence entries, including during a cron outage. At high traffic, useful retention can be shorter than seven days; if cron is disabled or cleanup fails and no volume cap is reached, time-based deletion is delayed. D1 recovery/backups and provider infrastructure metadata have their own policies. Existing application tables still hold functional metadata under the README's separate retention rules; this change does not remove that metadata.

Local iPhone/Watch exports retain the most recent 10,000 lines. The readable log file appends new rows and compacts back to 10,000 after a bounded overlap of at most 1,000 older rows; a restart prepares a protected snapshot before further appends. Routine fast successful status/heartbeat requests are sampled once per operation per 15 minutes; slow requests are retained as described below. Equivalent network errors and frequently repeated failure markers are sampled once per minute; the first network recovery is retained. Alert network attempts are always logged so each retains its request reference. These are diagnostic samples, not complete request counts. Protected atomic snapshots and subsequent appends retain Data Protection after first unlock and are excluded from backup. Failed appends are repaired from the bounded in-memory snapshot on the next write. The user explicitly copies/exports the iPhone log. Watch logs are viewable under Wrist alerts → Diagnostics. Both diagnostic screens render only the newest 200 lines to keep them responsive; iPhone Copy/Export and the device log retain the full history. Review exports before sharing: operational timestamps and request references can still reveal usage patterns.

Watch latency diagnostics added on 24 October 2026: local `watch_alert` rows include typed event/episode UUIDs and millisecond creation, OS delivery and callback timestamps. The existing Listener alert-request row now includes its event UUID alongside the server request reference, linking Watch observations to restricted backend diagnostics without extra requests. These identifiers are pseudonymous operational metadata; local exports can reveal alert timing and must be treated accordingly. The server journal's HMAC references and privacy contract above are unchanged. No payload text, device identity, push token, credential or audio is added. Each Watch event/phase is written once while retained in the 10,000-line ring; deduplication survives relaunch and evicted keys are discarded. Returning to the foreground reads retained notification metadata once per foreground invocation; it does not poll in the background, replay notifications or upload logs.

Cloudflare documents that automatic invocation logs include request/response metadata and URL-derived messages: [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/). Leave `[observability] enabled = false` in place. Avoid broad `wrangler tail`, request dumps, remote SQL dumps of functional tables, or enabling tracing as a default support procedure.

## Alert latency spans (25 October 2026)

Migration `0010_diagnostic_timings.sql` adds one nullable `details` JSON column to existing journal rows. Apply it before deploying this Worker. The seven-day expiry and 10,000-row cap still apply. Normal dispatches and connection notices retain one row per actual attempt; the opt-in phone-controlled Watch test also retains one `watch_test_dispatch` row per actual push, sharing the API request reference; stages do not issue individual journal writes. Only failed or unusually slow (at least two seconds) reminder scheduling adds a scheduling row, and failed alarms add a failure row.

The bounded allowlist contains numeric spans for authentication/rate limiting, alert preparation, the atomic suppression/claim batch, destination lookup, token decryption, provider signing, APNs response headers/body, outcome storage, reminder preparation and individual reminder queries. Reminder dispatch rows also carry alarm lateness when the persisted deadline exists. `generated_to_dispatch_ms` uses server event storage time for phone uploads and reminder-handler start for server reminders; it is not a cross-device total. Spans can be nested: do not add `handler_ms`, `reminder_prepare_ms`, and their child spans together. `elapsed_ms` ends before the journal insert itself.

Instrumented D1 calls also retain aggregate SQL duration, rows read/written and reported total attempts. `db_calls` counts instrumented binding calls, while `db_attempts` sums per-statement attempt metadata (a batch contains multiple statements). Calls in shared authentication/control helpers may have wall-time spans without D1 metadata and are excluded from those aggregate counts. SQL execution time does not include all binding/queue/network overhead. A fixed error category can identify an explicitly reported D1 overload/timeout; the raw error is never stored.

The reminder read-latency follow-up adds `db_stages`, keyed only by allowlisted span names. Each stage retains binding calls issued, completed calls, failed calls, returned statement count, provider-reported SQL milliseconds, rows read/written and total attempts. Missing provider metrics remain absent. Batch attempts sum across statements, so three reported attempts for a three-statement snapshot are not evidence of retries. `hedges` counts an extra read attempt, `hedge_wins` counts successful fallback results, and `unfinished` counts reads still outstanding when that logical read returned. Provider metrics cover only results observed before that return; a late loser is consumed without mutating the trace or generating additional journal rows. Nested stage names and fields are numerically allowlisted, with no SQL, results, tokens or raw errors retained.

Normal reminder preparation now has one read-only three-statement snapshot, an insert, and an atomic suppression/claim/token-selection batch: three binding calls before APNs instead of six. Snapshot wall time is `reminder_snapshot_ms`; pairing, control and latest-event SQL statements share the same transaction and have no fabricated individual wall times. Destination-token lookup is included in `claim_ms`; `destination_ms` remains available for other dispatch paths. The reminder heartbeat/original-event fallback reads also use the bounded read recovery below. Existing aggregate fields remain available and no schema migration is required.

Only these read-only reminder preparation calls may start one extra attempt after 1,500 ms, or immediately after the first attempt rejects. The first successful complete result wins; both failures retain the stage failure. There are at most two issued calls per logical read, and normal fast reads issue one. This is a bounded fallback, not an overall latency deadline: both provider calls can still stall. D1 does not cancel the losing query. No write, event insertion, claim transaction, outcome update or APNs request uses this fallback. The final atomic suppression/claim checks remain authoritative for Stop, acknowledgements, snooze and resolution, even when a preparation snapshot returns stale state. Existing unique reminder and claim constraints continue to suppress concurrent sends.

APNs details retain allowlisted Apple response reasons, including `TooManyRequests` versus `TooManyProviderTokenUpdates`, and safe fallback labels `unknown`/`unreadable`. Rejection-body reads are capped at 4 KiB and retain no body text. The journal may retain a format-validated Apple `apns-unique-id` solely to look up development delivery logs in Apple's Push Notifications Console, the development/production environment, provider-token cache hit/age, APNs request/response timestamps and timeout/network uncertainty. This is a narrowly allowed response identifier; arbitrary headers remain excluded. A validated three-letter Cloudflare colo helps distinguish request locations without retaining addresses. New identifiers are pseudonymous operational metadata and require the same restricted access as event references.

Phone `alert_outbox` rows record typed event UUIDs, exact creation and persistence/upload-start times, persistence duration and attempt number. Negative ages are retained with `clock_order=check`. This closes the local queue/persistence gap without automatic uploads. Local writes remain bounded by the existing 10,000-line policy. Watch OS delivery still does not prove haptic timing, and cross-device clocks still require checking.

For investigation, add `details` to the diagnostic SELECT below. Join initial API and dispatch rows using the server request reference, then follow `event_ref` for retries. APNs start-to-Watch is now separable from backend preparation when receipt evidence exists; APNs response-to-Watch is not a sequential last-mile measurement because delivery can precede the response reaching the Worker.

## Logging gap audit and fixes (25 October 2026)

The 08:12:22 reminder exposed an interleaving: D1 committed an insert, scheduled maintenance saw and claimed it, and the alarm's insert reply returned later. The losing alarm then silently returned from `dispatchEvent`, discarding its preparation timings. Every unsuccessful crying-alert claim now writes `dispatch_skip / claim_skipped` with the same keyed event reference and retained preparation spans. A best-effort read records the subsequently observed status, attempt count, retry deadline and fixed skip reason. That observation is not an atomic explanation of a concurrent state change. Only `operation = 'dispatch'` rows represent actual claimed attempts; count `dispatch_skip`, API rows and preparation records separately.

Preparation errors, guarded inserts producing no event, and stopped reminder loops now retain bounded `reminder_prepare` records. Fast mute/not-due passes still avoid an extra journal write; passes taking at least two seconds are retained. Timing starts before reminder queries and ends before dispatch; explicit preparation timestamps clarify that the reminder payload's creation timestamp predates its database reads/insertion. Alarm storage/arming errors are caught before preparation starts. Slow scheduling and finalization retain child storage/database spans, with internal server-generated request references connecting scheduler calls to the API/maintenance request. Failed-span labels preserve the innermost failure for one error, and a later distinct error replaces a previously handled failure.

Initial alert preparation now records pair lookup, event lookup/insert/reload, conflict lookup, and response-status read, including failures. API completion rows retain the keyed event reference, so an error before dispatch remains correlated. Dispatch rows preserve the known APNs outcome and HTTP status if the subsequent result-storage write fails. Connection notices get per-attempt start times, preparation/storage failure records, interrupted-lease diagnostics and skipped/cancelled outcomes. Phone-controlled Watch test pushes carry source and preparation timings too. Maintenance completion records distinguish expiry, lease recovery, pending selection, dispatch, schedule repair, connection work and cleanup; some run concurrently, so their durations are not an additive total. D1 metadata is optional: missing metrics never fail an otherwise successful operation, and `db_attempts` is recorded only when the provider reports it.

The response journal insert itself was outside `elapsed_ms`. API responses now expose its duration in numeric `x-diagnostics-elapsed-ms`, and phone network rows retain the validated value as `server_diagnostic_ms`. Successful status/heartbeat/timeline requests taking at least two seconds bypass routine success sampling, as do responses reporting a slow diagnostic write. Ordinary fast successes retain the existing sampling interval. `resume_alerts` networking and the `resume_alerts_failed`/`timeline_failed` markers are now included in the strict local allowlists; these had previously been silently dropped. Unknown event strings and untrusted header text remain excluded.

Watch cleanup observes and logs the already-fetched delivered notification metadata before Snooze or snapshot relevance removes it. This preserves receipts even when no presentation callback was captured; it adds no polling, push acknowledgement or automatic upload. Normal event/phase deduplication still makes repeated cleanup observations a no-op after the first retained record. New `controller_received`, `view_appeared`, and `snapshot_received` phases distinguish notification-controller callbacks, SwiftUI view appearance, and WatchConnectivity observations. Historical `presented` rows remain readable but represent the old controller callback label. Snapshot/haptic observations do not invent OS delivery dates. Unrecognized notification payload callbacks retain only a fixed marker and numeric source category. A notification view's acknowledgement keeps the delivery date captured for that same alert even if the hosting controller is reused.

All server details still pass the fixed-key/value allowlist and the existing seven-day / 10,000-row limits; phone/Watch logs keep their existing 10,000-line cap and protected append behavior. No migration is needed beyond already-deployed `0010`. Remaining limits: a process killed before it can complete a journal write can leave incomplete spans; a complete D1 outage can also prevent server diagnostics. Notifications dismissed by the system/user before this app can observe them may still lack a receipt. View/callback/haptic-request records do not establish physical vibration, and cross-device clock estimates require fresh valid samples as described below. The logger does not collect raw exceptions, SQL, bodies, tokens, addresses or credentials.

## Correlation, clocks, network phases and coverage follow-up

Crying and phone-controlled Watch test pushes now carry the existing keyed server event reference as `diagnosticRef` and the claimed delivery attempt as `deliveryAttempt`. They are diagnostic metadata, not acknowledgement authority. Watch logging accepts only a 64-character lowercase hexadecimal reference and a positive bounded integer attempt. `watch_alert` and notification-cleanup rows retain them, allowing exact `(event_ref, attempt)` joins to backend dispatches without timestamp inference or operator access to the HMAC key. Deduplication includes a validated attempt so a retry's receipt cannot hide behind an earlier attempt. Old payloads remain readable, and HMAC-computation failures remain best effort. No additional push or HTTP request is generated.

The existing HTTP response carries server-received and server-sent epoch milliseconds. The phone combines these with local request boundaries and a monotonic round-trip duration to estimate remote-minus-local clock offset and uncertainty. Invalid timestamps, impossible timing order and wall/monotonic disagreement exceeding 250 ms reject the sample; smaller disagreement increases uncertainty. Request durations and backend measured child spans use monotonic clocks. Creation/delivery timestamps and server diagnostic row timestamps remain wall-clock observations. Clock estimates do not silently rewrite those timestamps.

The Parent includes its current HTTP estimate in existing Watch snapshots. Only an existing live Watch request/reply supplies a phone↔Watch estimate: asynchronous/cached snapshots alone cannot calibrate the Watch. Composed estimates add uncertainty and a 100 ppm allowance for aging of the phone sample. Samples older than 15 minutes are unavailable. Estimates assume stable clocks during the exchanges; uncertainty is an estimate, not a guarantee about clock drift or physical notification delivery. Watch alert rows include available clock context and sample age. A Watch `clock_estimate` row is sampled once per 15 minutes; phone samples share existing retained network rows. There is no calibration polling.

The per-task URLSession delegate retains only a bounded scalar summary of at most 100 transactions. Slow requests (at least two seconds) and failures attach available DNS, connection, TLS, request, first-byte wait, response-transfer, total task and task-to-first-fetch durations, transaction/redirect counts and connection reuse counts to their existing network row. Missing metrics stay unavailable, not zero. Connection timing can include TLS; `server_wait_ms` includes network propagation and response scheduling as well as server processing, so these fields are not additive server execution spans. The collector never retains transaction objects, endpoints, URLs, header values, credentials or response bodies. See Apple's [task metrics](https://developer.apple.com/documentation/foundation/urlsessiontaskmetrics) and [transaction timing definitions](https://developer.apple.com/documentation/foundation/urlsessiontasktransactionmetrics).

Cleanup records identify a validated event/episode, delivered versus pending location, and the app's `removal_requested` action. Fixed reasons are `snoozed`, `test_acknowledged`, and `no_longer_relevant`; the last intentionally does not guess whether the server resolved, expired or otherwise retired the alert. A Watch Snooze may still await phone/server confirmation. Existing retained-receipt capture runs before removal; cleanup rows are appended in one batch. These records cannot establish an OS/user dismissal that the app did not observe, nor prove that the OS completed a requested removal.

Exports include first/last retained record times and process-scoped sampling, deduplication, eviction, read/write failure and recovery counts with a random process reference. Counts reset on relaunch and are explicitly labelled; historical checkpoints retain their own process reference. A coverage checkpoint is included at launch/foreground and after each 1,000 appended records, sharing the existing batched write. The in-memory/export header is current; persisted checkpoints reflect their observation time and may miss changes before a crash. Counters do not claim a complete request or delivery ledger. The 10,000-line ring, bounded compaction overlap and 200-line preview remain in force.

Backend journal writes still fail open. The next successful diagnostic row can report `journal_failures_before_write`, a best-effort isolate-local count of observed failures since the last successful report. A restart loses unreported counts, and concurrent reports can overlap, so do not sum this field across rows. This adds no recovery write or separate logging service, and retains no exception text. The response's existing unavailable marker remains useful when every journal write is failing.

## Durable acceptance and D1 latency follow-up (25 October 2026)

Time Sensitive support is now declared on the iOS companion as well as the Watch target. Updating source alone is insufficient: the signed phone app and its matching provisioning profile must contain `com.apple.developer.usernotifications.time-sensitive`. Existing notification preferences are preserved. Recheck `notification_time_sensitive_permission` on the phone and `watch_time_sensitive_permission` on the Watch after installation/foreground; raw `0` means not supported, `1` disabled, and `2` enabled. The Watch can mirror the companion's settings, so the Watch entitlement alone does not establish effective permission or Focus bypass. Startup marker `alert_pipeline_ready code=4` identifies this build. Physical first-vibration timing still requires a device test.

A reminder now uses two D1 binding calls before APNs on the ordinary path: one consistent read-only snapshot, then one atomic transaction containing reminder insertion, suppression guards, delivery claim and current destination token. The insert is included in `claim_ms` (five statements); it no longer has a separate `reminder_insert_ms`. This also closes the former insert/maintenance interleaving. Existing initial-upload insertion and claim safeguards, Snooze, resolution, Stop, token replacement, retry/backoff and uncertain-send behavior remain in force. Write claims are never hedged or automatically replayed.

After Apple explicitly accepts a delivery, the alarm checkpoints a functional receipt in its existing per-parent Durable Object. The alarm can complete while the D1 result write and journal continue in background work. Normal initial uploads also transfer accepted receipts to this object; their receipt and recovery alarm commit in one local transaction before returning. HTTP completion can report `sent` from that confirmed acceptance while the D1 row still says `sending`. Test pushes and callers without an execution context retain synchronous persistence. No public route accepts a delivery receipt.

Only a matching event, parent and attempt can use a durable receipt to treat a snapshot's `sending`/`uncertain` status as already accepted. Current D1 pairing, monitoring, mute, acknowledgement and resolution guards remain authoritative. A small isolate-local cache retains at most 128 accepted receipts so an in-flight snapshot cannot lose its evidence just because background persistence completed. Persistent receipts are deleted after D1 confirms the result and its journal attempt completes. They contain functional event/parent identifiers, attempt, acceptance time, retry deadline and a strictly sanitized diagnostic capsule, never a token or payload. They are functional recovery state, separate from the diagnostic ring's retention limits.

Persistence processes at most 16 receipts per pass with fan-out four and one flusher per object. Failures retain the receipt for another alarm, including during Snooze or after delivery stops. Recovery only updates D1; it never resends APNs. The update is scoped to the same event, parent and attempt and can repair cron's `dispatch_interrupted` lease status without clearing acknowledgement/resolution or overwriting a later attempt. Initial persistence writes the usual `dispatch` row; recovered writes use `dispatch_outcome`, so they must not be counted as new push attempts. `durable_outcome`, `outcome_recovery`, `outcome_queue_age_ms`, and available `outcome_queue_ms` separate checkpointing from later persistence. A crash before local checkpoint completion can still leave an accepted push without a durable receipt; the existing uncertain-send rules prevent blind replay.

Database stages now retain at most 16 bounded per-statement metadata entries: statement index, available SQL time and attempt count, validated serving colo/region, and primary/replica boolean. Stage `retries` sums only excess attempts beyond the first per statement; four statements with four total attempts means zero retries. Unknown provider fields, SQL text/parameters and arbitrary metadata strings remain excluded. Optional missing/malformed metrics never fail a successful call. A result journal taking at least two seconds emits one additional `dispatch_outcome / cleanup / ok` row with `journal_ms`; it never recursively logs its own duration. Most deliveries still use one journal row.

These changes reduce exposure to D1 round trips and prevent slow accepted-result persistence from blocking the next reminder. They do not remove a slow pre-send claim or identify Cloudflare's internal transport/scheduling cause. The incident's 6.6-second claim reported 1.334 ms of SQL; independent server-side D1 analytics were also fast. The database was already in Western Europe. Read replicas do not accelerate write claims and are not enabled by this change. No new infrastructure service, D1 migration, polling request or notification cadence change is required.

Verification includes real D1 transactions, duplicate-claim races, a stalled accepted-result write overlapping the next alarm, stale snapshots outliving receipt deletion, recovery after restart/write failure and Snooze, later-attempt protection, ambiguous-APNs exclusion, initial-upload handoff, metadata sanitization and bounds. Background work is attached to the object's lifetime while the alarm handler completes; this matches the runtime's [alarm/background drain implementation](https://github.com/cloudflare/workerd/blob/main/src/workerd/io/worker-entrypoint.c%2B%2B).

## Investigating an incident

1. Record approximate incident time/timezone and whether it involved detection, delivery, phone presentation or Watch presentation. Export iPhone diagnostics promptly from Settings → Diagnostics & simulation. For wrist-only symptoms inspect the Watch's Diagnostics screen too.
2. Find `network operation=... outcome=... request_id=...` around the failure. `transport_error` has a numeric URL error and often no response reference because no server response arrived. `decode_error` means an HTTP response arrived but did not match the app's expected data.
3. In Cloudflare's D1 console, query **only** diagnostic columns using the request UUID from the export:

   ```sql
   SELECT datetime(recorded_at/1000, 'unixepoch') AS utc,
          request_id, operation, stage, outcome, http_status,
          elapsed_ms, event_ref, attempt, target, release, details
   FROM diagnostics
   WHERE request_id = 'REPLACE-WITH-REQUEST-UUID'
   ORDER BY sequence;
   ```

4. For a dispatch row, query the same columns with `WHERE event_ref = 'REFERENCE-FROM-THAT-ROW' ORDER BY sequence` to follow cron retries. Do not query or share credentials/tokens/payloads. `release` identifies the Worker build to inspect; retain the matching source revision with deployment records.
5. Interpret the outcome:

   | Outcome | Meaning/action |
   | --- | --- |
   | `no_push_token`, `invalid_device_token` | Parent/Watch has no usable destination; check permission, signing/topic/environment and registration. |
   | `token_decryption` | Stored token cannot be decrypted with current configuration; inspect secret rotation/deployment, then re-register as appropriate. |
   | `provider_signing`, `provider_configuration`, `apns_environment` | Inspect APNs secret presence/format, key/team permissions, topic and development/production configuration without printing secrets. |
   | `apns_429`, `apns_500`, `apns_503` | Explicit retryable APNs response. Follow later attempts and cron health. |
   | `bad_topic`, `missing_topic`, `bad_priority`, `bad_expiration`, `bad_payload`, `payload_too_large`, `apns_rejected` | Explicit terminal rejection. Use the category, HTTP status and matching release to inspect payload construction. Unknown rejection text is deliberately discarded. |
   | `transport_unknown`, `dispatch_interrupted` | Acceptance is ambiguous. Check receiving devices; do not manually resend without evaluating duplicate risk. |
   | `sent` | APNs accepted the request. It does not prove phone/Watch display or haptic delivery. |
   | `internal_error` | Inspect operation/stage and matching release. Reproduce with synthetic data; raw production exceptions are deliberately not collected. |

6. Check cron liveness without reading functional metadata:

   ```sql
   SELECT datetime(MAX(recorded_at)/1000, 'unixepoch') AS last_success_utc
   FROM diagnostics WHERE operation = 'maintenance' AND outcome = 'ok';
   ```

   A missing or several-minutes-old result needs investigation. Check Cloudflare invocation/error metrics and configured cron trigger. Successful cron with no pending alerts still writes a completion row. `server_diagnostics=unavailable` in an app export signals missing journal evidence, not successful persistence.

## Remaining limits and operational work

- Deploy migration `0003_diagnostics.sql` before the updated Worker so diagnostic persistence is available. Rebuild/install both phone and Watch apps. These changes alone do not alter the live service.
- No automatic backend/cron outage notification or independent synthetic monitoring is configured. The optional Listener connection notices introduced in `0004_readiness.sql` require the backend and minute cron to remain healthy. Operators need a check for stale cron completion, elevated 503s, blocked/uncertain alerts and diagnostic storage failures. Do not point an unattended monitor at real child data; use a dedicated synthetic pair and define cleanup/notification ownership.
- The journal shares D1 with the application. A total D1 outage can prevent both application work and server diagnostic persistence. Client exports and Cloudflare aggregate metrics are the fallback. A killed Worker can leave no completion record; lease recovery records the affected dispatch on the next cron run.
- App logs cannot execute after a crash, force quit, watchdog kill or OS termination. Collect the matching iOS/watchOS crash, hang or jetsam report through Xcode/device diagnostics or Organizer, with user consent. Keep the exact release archive and dSYMs for symbolication. No crash/MetricKit upload SDK is installed by this change.
- Log sampling/caps intentionally trade exhaustive history for privacy, storage and performance. No source review can guarantee every future issue is diagnosable. Physical locked-screen, interruption, offline/reconnect, Focus/Silent Mode, wrist delivery and overnight checks still matter.

## Initial upload stalls and request correlation (25 October 2026)

The 20:39:33.532 alert reached the Watch OS after 31.949 seconds. Its first phone request timed out after 20.284 seconds; the successful retry spent 9.188 seconds before starting APNs (4.803 authentication, 1.538 rate limiting, 2.586 preparation, 0.260 claiming, plus rounding). The event lookup awaited D1 for 2.521 seconds while its reported SQL duration was 0.431 ms. The first invocation did not leave a completed correlated API row, so its full timeout cannot be allocated. This identifies waits outside SQL execution, without identifying a particular provider queue, network hop or runtime scheduler as the root cause. Cloudflare's [D1 metadata](https://developers.cloudflare.com/api/resources/d1/) excludes network time from SQL duration; its [throughput guidance](https://developers.cloudflare.com/d1/platform/limits/) recommends batching to reduce per-request overhead.

The normal new initial-alert path now makes four sequential D1 calls before APNs, previously seven: authenticated admission, pair/event snapshot, insert/reload, then the existing suppression/claim/token transaction. Admission batches a fresh device read with the existing dedicated alert-budget write. That write is gated on the device ID and secret hash in the same transaction, so invalid/revoked credentials cannot consume another device's budget. Constant-time credential verification still determines authentication, all 600-per-ten-minute alert-budget enforcement remains synchronous, and no credential cache is used. The initial snapshot has the existing bounded SELECT-only fallback (one additional call after 1.5 seconds); mutation batches and APNs are never hedged. Concurrent metadata/episode conflicts, exact pairing guards, Stop, Snooze, resolution, expiry, uncertainty and delivery claims retain their existing behavior. An existing event skips insertion/reload.

`alert_admission_ms` and `alert_snapshot_ms` now include per-statement D1 serving/retry/SQL evidence. `event_insert_ms` includes insertion plus the transactional reload; `authentication_hash_ms` measures local credential/budget hashing and `body_read_ms` measures request decoding. These replace the separate authentication/rate-limit and pair/lookup/reload timings on this upload route. Other routes retain their previous timings. Fewer binding calls reduce serial overhead; this does not impose a hard bound on provider write latency or prove the provider stall is resolved.

Pipeline version 5 generates a fresh `X-Client-Request-ID` UUID for each phone alert transport attempt. One `alert_upload phase=started` row saves it with the existing functional event UUID before networking. The existing network completion/failure row retains the same `client_request_id`, even when no server response/request ID arrives. Retries keep the same event UUID and get different client attempt UUIDs. The server retains only validated UUIDs in `details.client_request_id`; this is diagnostic correlation, never authentication or idempotency authority. No device identifiers, credentials, headers, SQL or payloads are added to diagnostics.

For an initial upload still running at ten seconds, one asynchronous `alert_progress / still_running` journal attempt captures the current `in_flight_span`, `in_flight_ms`, completed stages, request IDs and any event reference already known. The sanitized snapshot is frozen before journal I/O. The timer is cancelled for fast requests, adds no ordinary diagnostic write, and never gates delivery; a started journal remains in `waitUntil` until completion. There is no polling or repeating checkpoint. D1 itself stores this evidence, so a database outage or killed invocation can still lose it. The new client attempt ID allows a later completed server row to be found even after the phone's request timed out.

## Remaining D1 waits and Watch presentation (25 October 2026)

The post-upload-fix batch had a 182 ms initial backend path, but one reminder still awaited its snapshot for 1,519 ms and its claim for 895 ms. The winning snapshot and claim reported only 0.772 and 1.965 ms of SQL respectively. The same four-minute window contained 95 successful status handlers; nine took at least two seconds, with separate journal waits also visible on the phone. This identifies waits outside SQL execution, not a proven provider queue or SQL-capacity overload. App-side work can be reduced without claiming that all provider latency is controllable.

Status handlers now use a pair read and one five-statement consistent snapshot instead of a pair read and five independent requests. The snapshot rechecks the exact pairing generation and returns an unpaired response if it changed. With authentication and both existing synchronous rate limits, this reduces a normal status request from nine binding calls before journaling to five. API traces now include `ip_rate_limit_ms`, `device_rate_limit_ms`, `authentication_lookup_ms`, `status_pair_ms` and `status_snapshot_ms` with per-statement metrics.

In production, successful status journaling uses `waitUntil`, so a slow log write cannot delay the status response. Ordinary fast status successes retain one representative row per 30 seconds per isolate; every handler taking at least two seconds and every failure remains eligible for a row. `status_successes_sampled` reports omitted ordinary successes since that isolate's last sampling decision; it is not a per-device/global request count, and an isolate exit or failed journal can lose it. Headers distinguish `queued` from `sampled`; the phone preserves those values without treating them as proof of persistence. Responses report zero synchronous diagnostic time. A journal await of at least two seconds produces one best-effort `status_journal` observation without recursive timing. Requests without an execution context keep the synchronous diagnostic path. Alert, dispatch, heartbeat, maintenance and failure retention are unchanged; the seven-day/10,000-row bounds remain.

Initial and reminder read snapshots still issue at most one fallback SELECT-only batch, now at 250 ms rather than 1,500 ms. `hedge_after_ms` records that threshold and `hedge_timer_lag_ms` records delayed timer execution, so runtime scheduling cannot be silently confused with the configured fallback delay. There is no polling or third attempt. Normal fast reads issue one call.

Migration `0011_claim_ownership.sql` adds an internal per-invocation claim UUID. A slow delivery claim may issue one receipt SELECT after 250 ms, or after its original write rejects. That SELECT must find this exact invocation's committed ownership; a different sender's claim or a missing row never authorizes APNs. A matched receipt rechecks current pairing, acknowledgement/resolution, status, lease and the current selected-target token. It may replace a delayed/lost write reply without issuing another write or push. If the receipt is absent/unavailable, the code waits for the original result, or fails closed when the original also failed. Expired leases do not send, even when an original reply arrives late. This is conditional progress after durable proof, not a mutation retry or a bound on uncommitted write latency.

`claim_result_source` distinguishes `reply` and `receipt`, and `claim_receipt_outcome` distinguishes matched/missing/error. `claim_receipt_ms` is a child of `claim_ms`. When a receipt wins, the original claim stage has `unfinished=1`, and its SQL metrics remain unavailable; they are not fabricated from the proof. When the original reply wins during a receipt read, the receipt stage records `unfinished=1`. Late results/rejections do not mutate the frozen dispatch trace. The ownership UUID and encrypted token are functional data, not diagnostic fields or client authority. Background acceptance persistence and maintenance dispatch each use at most two workers to leave connection capacity for foreground claims and proof reads. Current suppression checks, deduplication, uncertainty policy, accepted-result recovery and reminder cadence remain in force.

Successful Apple responses explicitly cancel an unused body without awaiting cleanup or changing known acceptance. Under current [Workers connection limits](https://developers.cloudflare.com/workers/platform/limits/#simultaneous-open-connections), headers release the connection slot; this cleanup is resource hygiene, not evidence that unread APNs bodies caused the observed stalls.

The Watch custom controller is the [long-look notification interface](https://developer.apple.com/documentation/watchos-apps/presenting-notifications-on-apple-watch). watchOS controls the initial short look and transition to full details; a controller callback is not the first banner/haptic. The observed controller-to-view gaps were roughly 60–90 ms while most logged delay preceded controller entry. Pipeline 6 requests foreground banner/list/sound presentation immediately, before parsing, model initialization, main-actor dispatch or diagnostic I/O. Custom long-look content is populated from the payload; model/log work yields out of the controller callback and view appearance handler. The inline Snooze remains.

Watch trace rows add fixed `callback_scope`, app state at diagnostic processing, bounded `presentation_request_ms`, `main_actor_wait_ms`, `app_handling_ms`, and the numeric delivered interruption level where available. `controller_activated`/`controller_deactivated` phases separate controller lifecycle from notification receipt and view appearance. Captured callback timestamps survive deferred logging. Long-look `app_handling_ms` measures payload preparation, and foreground `app_handling_ms` measures model preparation before the log write; neither claims to time the log write itself. Lifecycle rows share the existing per-event/phase/attempt deduplication and bounded ring. These changes remove app-controlled presentation work and improve measurement; they cannot force watchOS to reveal full details or establish physical haptic latency. A system long-look view is an alternative, retaining registered Snooze as an action but losing the custom top-position button; it is not selected automatically by this rollout.

### Heartbeat waits and independent Watch callback journal — 25 October 2026

Heartbeat success now uses four functional D1 binding calls, previously eight while monitoring: a fresh credential SELECT, a single quota/admission transaction, one joined pairing/previous-heartbeat snapshot, and one atomic persistence/configuration batch. The credential and snapshot SELECTs each permit one read-only fallback after 250 ms (or early rejection). Neither admission nor heartbeat writes are replayed. Admission revalidates the credential in its transaction, retains the existing IP/device quota keys and ceilings, counts rejected credentials against the IP budget and does not charge the device when IP admission fails. Valid-header credential lookup precedes IP quota admission on this route; an over-budget caller can incur that extra read before rejection. No cached authentication is introduced.

The heartbeat persistence batch includes guarded metadata, timeline/quiet-resolution writes, initial online state and the final exact-pair configuration read. A server-generated random receipt in the stored heartbeat JSON proves this entire transaction committed. After 250 ms, or a lost write reply, at most one SELECT may recover that exact receipt with the same current pairing and return fresh configuration. A different/overwritten receipt or removed pairing cannot authorize recovery; the request awaits the original reply or fails closed. The write executes once, with no new table or migration. `heartbeat_result_source`, `heartbeat_receipt_outcome` and the child `heartbeat_receipt_ms` distinguish logical completion from the original write reply; unfinished write SQL metrics stay unknown. The internal receipt is never accepted from clients, returned by the API or included in diagnostics. An intervening pairing change cannot resurrect old data. The rare muted-crying reminder re-arm remains awaited and separately timed. `authentication_lookup_ms`, `heartbeat_admission_ms`, `heartbeat_snapshot_ms`, `heartbeat_storage_ms` and `heartbeat_schedule_ms` identify the remaining waits and SQL/provider metrics. Successful heartbeat journals use `waitUntil`, are never sampled, and return `x-diagnostics-status: queued` with zero synchronous journal wait. Slow journal writes add one bounded `heartbeat_journal` observation; failures retain the existing synchronous error path. A provider write that has not completed can still stall, and successful background journals remain best effort.

Watch pipeline 7 adds an independent callback-entry journal in Application Support: `watch-callbacks.log` and `watch-callbacks.previous.log`, each bounded to 2 MiB. Entries append under a short process-local lock without a main-actor hop, model initialization, fsync, network request or wakeup. Foreground OS presentation completion still runs before parsing/journaling. Long-look entry performs one small journal append before deferring model work; its added `journal_write_ms` is measured separately from payload handling and main-actor queue wait. Rotation occurs only when a segment fills. Open repairs an incomplete trailing record; byte rotation, write failures and repairs are reported in coverage checkpoints. Files are excluded from backup and available after first unlock. App lifecycle, process ID, continuous process elapsed time, sequence, callback ID, event reference and attempt distinguish cold launch, repeated callbacks and missing deferred-log completion. Journal append success does not promise power-loss durability.

Actual callback instances receive distinct `callback_id` values and are preserved across repeated long-look activations/relaunches instead of being suppressed by event/phase deduplication. The normal diagnostic ring still holds 10,000 lines and joins the entry journal by callback ID. History scans remain deduplicated and report `history_observation_lag_ms` and `history_source`; user actions report `user_action_lag_ms`. Only actual callback phases retain `callback_lag_ms`. Recovered history also records delivered interruption level and whether its request identifier matches the event or episode (`collapse_scope`); arbitrary request identifiers never enter logs. Callback application state is sampled when processed, not inferred retrospectively at entry.

Collect all three files before opening the app, where possible:

```sh
python3 scripts/collect-watch-diagnostics.py --device WATCH_COREDEVICE_ID --output LOCAL_EVIDENCE_DIRECTORY
```

The collector only copies files. An absent previous segment is normal before rotation; unavailable current logs are an error. Compare raw `watch_callback` entries with deferred `watch_alert` entries by callback ID. A raw entry without its deferred counterpart establishes callback entry despite missing model-log work. An event with history but no callback entry means no callback was observed in retained coverage; it does not prove no banner or haptic. Collapsed/replaced reminders cannot all be recovered from Notification Center history, and instrumentation cannot force watchOS to execute a long-look or background callback. No diagnostic-only notification identifiers, extra pushes or background polling are added.


## Phone notification receipts and both-device delivery (25 October 2026)

`phone_notification` retains a validated event UUID, episode UUID, OS `UNNotification.date`, numeric interruption level and fixed observation phase (`foreground`, `opened`, `retained`). Retained observations are captured at registration and before notification cleanup; they do not manufacture a foreground callback. Duplicate event/phase observations are suppressed with a bounded in-memory set. No notification text, token, device credential, automatic upload or polling is added. An OS receipt establishes delivery to Notification Center, without proving visual interruption, Focus bypass, sound or wrist vibration.

New both-device dispatch records contain one target-specific `dispatch` row per attempted destination and an untargeted `dispatch_outcome` carrying aggregate preparation/claim timings. `delivery_state` is functional persistent per-target recovery state, not a new diagnostic store. Accepted, uncertain and terminally failed targets are not replayed when the other destination retries. An interrupted aggregate with two persisted acceptances can be repaired to `sent`; ambiguous sends remain uncertain. Existing single-device completed events are not replayed during migration.

## APNs provider-token reuse (25 October 2026)

Apple's `TooManyProviderTokenUpdates` response rejects authentication-token churn, separately from notification-volume `TooManyRequests`. A per-isolate cache lost on eviction/deployment also allowed concurrent cold sends to sign different JWTs. For the 22:39:50.077 event, the Watch receipt arrived after 156 ms while the phone retried two such rejections and arrived after 16.104 seconds. A single credential-scoped `ProviderTokens` SQLite Durable Object now persists the JWT before returning it and coalesces signing through its durable write. Fresh Worker/Reminder instances retrieve that same token; local memory and an in-flight promise avoid repeated coordination for warm or concurrent sends. Tokens rotate lazily at 50 minutes, within Apple's [20–60 minute refresh window](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns). Topics and sandbox/production share the same credential authority. Normalized signing credentials select its identity, so configuration changes cannot receive a mismatched token. Coordinator failures never fall back to independent local signing.

Existing target-specific dispatch rows retain `provider_token_age_s` and `provider_token_cached`, adding the allowlisted `provider_token_source` (`memory`, `in_flight`, `coordinator_reused`, `coordinator_created`) and a SHA-256 `provider_token_ref`. The latter fingerprints the high-entropy signed JWT, not a device identifier; it is not usable as a bearer token. `provider_sign_ms` now includes token-authority acquisition on a cold miss and remains a local cache lookup on a warm send. JWTs and signing credentials never enter diagnostic rows or responses to public API clients. The existing journal retention and volume cap apply.

`POST /v1/diagnostics/apns` authenticates a Parent device and applies an additional six-per-ten-minute device budget. It always checks the authority, never forces early rotation, never contacts APNs and returns only readiness, token fingerprint, age and source. It supports verifying persistent reuse in production without notifying a device. A successful check proves signing/coordination readiness, not Apple acceptance or notification delivery. Actual post-deployment dispatch rows are required to measure rejection frequency and receiver latency; existing Apple throttling may persist temporarily after correcting churn. Existing retry, per-destination acceptance and transport-uncertainty handling are unchanged.

The follow-up review reproduced a response crossing the 50-minute refresh deadline in transit and being rejected even though its JWT remained usable. Response validation now permits that in-flight token up to age 59 minutes, reserving one minute before Apple's expiry. Local cache hits and authority rotation still stop at 50 minutes, so the next lookup refreshes through the same authority. Tokens at or beyond 59 minutes, future-dated records and mismatched credentials remain rejected. Regression tests cover the boundary, expiry rejection and recovery, and twelve concurrent cold clients through the actual Durable Object binding.

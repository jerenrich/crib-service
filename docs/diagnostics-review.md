## Findings and changes

| Area | Finding | Result |
| --- | --- | --- |
| Server API | Unexpected errors became a generic 503 with no retained evidence. No app/server correlation. | Restricted D1 journal records operation, stage, outcome, HTTP status, elapsed time, server-generated request reference and deployed Worker version. Every API response includes `x-request-id`. |
| APNs and retry queue | Current event status/attempt count existed, but the history of attempts and cron recovery was missing. | Journal records accepted/rejected/blocked/ambiguous delivery, attempts, destination, preparation failures, safe APNs categories and interrupted claims. Keyed event references connect API and scheduled attempts. |
| Diagnostic failure | The app silently ignored file failures. | Visible persistence health, in-memory export fallback, atomic protected writes and exclusion from backups. Server journal failure never changes alert delivery; API responses report `x-diagnostics-status: unavailable`. |
| App networking | Most errors were visible only until another status replaced them. | Logs fixed operation/outcome categories, numeric HTTP/URL error codes, response request reference and elapsed time. Covers errors decoding successful responses too. |
| App lifecycle and audio | Recovery reasons, credential/storage failures and relaunch context were incomplete. | Build/OS export header, launch/foreground/background markers, permission and capture recovery categories, storage/credential failures and delivery states. No audio levels are added to the log. |
| Phone and Watch | Notification permission/registration and Watch sync failures were largely transient UI text. | Local permission, registration, receipt, sync and acknowledgement markers; numeric error codes where available. Watch has its own on-device diagnostic screen. |
| Privacy | Enabling normal server logging would introduce request metadata collection. | Automatic Worker observability stays disabled. Dedicated diagnostic columns prevent payload/exception serialization. No automatic app-log upload or third-party SDK. |

## Privacy and retention contract

Server diagnostic rows contain operational timestamps, a random request UUID, fixed operation/stage/outcome labels, numeric status/duration/attempts, phone/watch destination, a Worker release UUID and optional HMAC-SHA256 event reference. The HMAC is namespaced and keyed using the existing server pepper. It does not hash or retain device identity. References identify an event across retries; they are pseudonymous, not anonymous, and must be treated as sensitive operational data.

No diagnostic row contains request or response bodies, arbitrary URLs/paths/query strings, arbitrary headers, IP addresses, device UUIDs, episode/event UUIDs, pairing codes, push tokens, credentials, configuration values, battery readings, crying timestamps/durations, audio/features or raw exception messages/stacks. Unknown routes and APNs reasons map to fixed fallback labels. Incoming correlation IDs are ignored. Diagnostics are accessible through operator D1 access only; there is no diagnostic API endpoint.

The minute cron attempts to delete journal rows older than seven days **before** delivery work. Cleanup failure records `diagnostic_cleanup_failed` when journal writes remain available, and allows alert delivery to continue. An insertion trigger caps the journal at the most recent 10,000 sequence entries, including during a cron outage. At high traffic, useful retention can be shorter than seven days; if cron is disabled or cleanup fails and no volume cap is reached, time-based deletion is delayed. D1 recovery/backups and provider infrastructure metadata have their own policies. Existing application tables still hold functional metadata under the README's separate retention rules; this change does not remove that metadata.

Local iPhone/Watch exports retain the most recent 10,000 lines. The readable log file appends new rows and compacts back to 10,000 after a bounded overlap of at most 1,000 older rows; a restart prepares a protected snapshot before further appends. Routine fast successful status/heartbeat requests are sampled once per operation per 15 minutes; slow requests are retained as described below. Equivalent network errors and frequently repeated failure markers are sampled once per minute; the first network recovery is retained. Alert network attempts are always logged so each retains its request reference. These are diagnostic samples, not complete request counts. Protected atomic snapshots and subsequent appends retain Data Protection after first unlock and are excluded from backup. Failed appends are repaired from the bounded in-memory snapshot on the next write. The user explicitly copies/exports the iPhone log. Watch logs are viewable under Wrist alerts → Diagnostics. Both diagnostic screens render only the newest 200 lines to keep them responsive; iPhone Copy/Export and the device log retain the full history. Review exports before sharing: operational timestamps and request references can still reveal usage patterns.

Watch latency diagnostics added on 24 October 2026: local `watch_alert` rows include typed event/episode UUIDs and millisecond creation, OS delivery and callback timestamps. The existing Listener alert-request row now includes its event UUID alongside the server request reference, linking Watch observations to restricted backend diagnostics without extra requests. These identifiers are pseudonymous operational metadata; local exports can reveal alert timing and must be treated accordingly. The server journal's HMAC references and privacy contract above are unchanged. No payload text, device identity, push token, credential or audio is added. Each Watch event/phase is written once while retained in the 10,000-line ring; deduplication survives relaunch and evicted keys are discarded. Returning to the foreground reads retained notification metadata once per foreground invocation; it does not poll in the background, replay notifications or upload logs.

Cloudflare documents that automatic invocation logs include request/response metadata and URL-derived messages: [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/). Leave `[observability] enabled = false` in place. Avoid broad `wrangler tail`, request dumps, remote SQL dumps of functional tables, or enabling tracing as a default support procedure.

## Alert latency spans (25 October 2026)

Migration `0010_diagnostic_timings.sql` adds one nullable `details` JSON column to existing journal rows. Apply it before deploying this Worker. The seven-day expiry and 10,000-row cap still apply. Normal dispatches and connection notices retain one row per actual attempt; the opt-in phone-controlled Watch test also retains one `watch_test_dispatch` row per actual push, sharing the API request reference; stages do not issue individual journal writes. Only failed or unusually slow (at least two seconds) reminder scheduling adds a scheduling row, and failed alarms add a failure row.

The bounded allowlist contains numeric spans for authentication/rate limiting, alert preparation, the atomic suppression/claim batch, destination lookup, token decryption, provider signing, APNs response headers/body, outcome storage, reminder preparation and individual reminder queries. Reminder dispatch rows also carry alarm lateness when the persisted deadline exists. `generated_to_dispatch_ms` uses server event storage time for phone uploads and reminder-handler start for server reminders; it is not a cross-device total. Spans can be nested: do not add `handler_ms`, `reminder_prepare_ms`, and their child spans together. `elapsed_ms` ends before the journal insert itself.

Instrumented D1 calls also retain aggregate SQL duration, rows read/written and reported total attempts. `db_calls` counts instrumented binding calls, while `db_attempts` sums per-statement attempt metadata (a batch contains multiple statements). Calls in shared authentication/control helpers may have wall-time spans without D1 metadata and are excluded from those aggregate counts. SQL execution time does not include all binding/queue/network overhead. A fixed error category can identify an explicitly reported D1 overload/timeout; the raw error is never stored.

The reminder read-latency follow-up adds `db_stages`, keyed only by allowlisted span names. Each stage retains binding calls issued, completed calls, failed calls, returned statement count, provider-reported SQL milliseconds, rows read/written and total attempts. Missing provider metrics remain absent. Batch attempts sum across statements, so three reported attempts for a three-statement snapshot are not evidence of retries. `hedges` counts an extra read attempt, `hedge_wins` counts successful fallback results, and `unfinished` counts reads still outstanding when that logical read returned. Provider metrics cover only results observed before that return; a late loser is consumed without mutating the trace or generating additional journal rows. Nested stage names and fields are numerically allowlisted, with no SQL, results, tokens or raw errors retained.

Normal reminder preparation now has one read-only three-statement snapshot, an insert, and an atomic suppression/claim/token-selection batch: three binding calls before APNs instead of six. Snapshot wall time is `reminder_snapshot_ms`; pairing, control and latest-event SQL statements share the same transaction and have no fabricated individual wall times. Destination-token lookup is included in `claim_ms`; `destination_ms` remains available for other dispatch paths. The reminder heartbeat/original-event fallback reads also use the bounded read recovery below. Existing aggregate fields remain available and no schema migration is required.

Only these read-only reminder preparation calls may start one extra attempt after 1,500 ms, or immediately after the first attempt rejects. The first successful complete result wins; both failures retain the stage failure. There are at most two issued calls per logical read, and normal fast reads issue one. This is a bounded fallback, not an overall latency deadline: both provider calls can still stall. D1 does not cancel the losing query. No write, event insertion, claim transaction, outcome update or APNs request uses this fallback. The final atomic suppression/claim checks remain authoritative for Stop, acknowledgements, snooze and resolution, even when a preparation snapshot returns stale state. Existing unique reminder and claim constraints continue to suppress concurrent sends.

APNs details retain allowlisted Apple response reasons, including `TooManyRequests` versus `TooManyProviderTokenUpdates`, and safe fallback labels `unknown`/`unreadable`. Rejection-body reads are capped at 4 KiB and retain no body text. The journal may retain a format-validated Apple `apns-unique-id` solely to look up development delivery logs in Apple's Push Notifications Console, the development/production environment, provider-token cache hit/age, APNs request/response timestamps and timeout/network uncertainty. This is a narrowly allowed response identifier; arbitrary headers remain excluded. A validated three-letter Cloudflare colo helps distinguish request locations without retaining addresses. New identifiers are pseudonymous operational metadata and require the same restricted access as event references.

Phone `alert_outbox` rows record typed event UUIDs, exact creation and persistence/upload-start times, persistence duration and attempt number. Negative ages are retained with `clock_order=check`. This closes the local queue/persistence gap without automatic uploads. Local writes remain bounded by the existing 10,000-line policy. Watch OS delivery still does not prove haptic timing, and cross-device clocks still require checking.

For investigation, add `details` to the diagnostic SELECT below. Join initial API and dispatch rows using the server request reference, then follow `event_ref` for retries. APNs start-to-Watch is now separable from backend preparation when receipt evidence exists; APNs response-to-Watch is not a sequential last-mile measurement because delivery can precede the response reaching the Worker.

## Logging gap audit and fixes (25 October 2026)

The 08:12:22 reminder exposed an interleaving: D1 committed an insert, scheduled maintenance saw and claimed it, and the alarm's insert reply returned later. The losing alarm then silently returned from `dispatchEvent`, discarding its preparation timings. Every unsuccessful crying-alert claim now writes `dispatch_skip / claim_skipped` with the same keyed event reference and retained preparation spans. A best-effort read records the subsequently observed status, attempt count, retry deadline and fixed skip reason. That observation is not an atomic explanation of a concurrent state change. Only `operation = 'dispatch'` rows represent actual claimed attempts; count `dispatch_skip`, API rows and preparation records separately.

Preparation errors, guarded inserts producing no event, and stopped reminder loops now retain bounded `reminder_prepare` records. Fast mute/not-due passes still avoid an extra journal write; passes taking at least two seconds are retained. Timing starts before reminder queries and ends before dispatch; explicit preparation timestamps clarify that the reminder payload's creation timestamp predates its database reads/insertion. Alarm storage/arming errors are caught before preparation starts. Slow scheduling and finalization retain child storage/database spans, with internal server-generated request references connecting scheduler calls to the API/maintenance request. Failed-span labels preserve the innermost failure for one error, and a later distinct error replaces a previously handled failure.

Initial alert preparation now records pair lookup, event lookup/insert/reload, conflict lookup, and response-status read, including failures. API completion rows retain the keyed event reference, so an error before dispatch remains correlated. Dispatch rows preserve the known APNs outcome and HTTP status if the subsequent result-storage write fails. Connection notices get per-attempt start times, preparation/storage failure records, interrupted-lease diagnostics and skipped/cancelled outcomes. Phone-controlled Watch test pushes carry source and preparation timings too. Maintenance completion records distinguish expiry, lease recovery, pending selection, dispatch, schedule repair, connection work and cleanup; some run concurrently, so their durations are not an additive total. D1 metadata is optional: missing metrics never fail an otherwise successful operation, and `db_attempts` is recorded only when the provider reports it.

The response journal insert itself was outside `elapsed_ms`. API responses now expose its duration in numeric `x-diagnostics-elapsed-ms`, and phone network rows retain the validated value as `server_diagnostic_ms`. Successful status/heartbeat/timeline requests taking at least two seconds bypass routine success sampling, as do responses reporting a slow diagnostic write. Ordinary fast successes retain the existing sampling interval. `resume_alerts` networking and the `resume_alerts_failed`/`timeline_failed` markers are now included in the strict local allowlists; these had previously been silently dropped. Unknown event strings and untrusted header text remain excluded.

Watch cleanup observes and logs the already-fetched delivered notification metadata before Snooze or snapshot relevance removes it. This preserves receipts even when no presentation callback was captured; it adds no polling, push acknowledgement or automatic upload. Normal event/phase deduplication still makes repeated cleanup observations a no-op after the first retained record. New `controller_received`, `view_appeared`, and `snapshot_received` phases distinguish notification-controller callbacks, SwiftUI view appearance, and WatchConnectivity observations. Historical `presented` rows remain readable but represent the old controller callback label. Snapshot/haptic observations do not invent OS delivery dates. Unrecognized notification payload callbacks retain only a fixed marker and numeric source category. A notification view's acknowledgement keeps the delivery date captured for that same alert even if the hosting controller is reused.

All server details still pass the fixed-key/value allowlist and the existing seven-day / 10,000-row limits; phone/Watch logs keep their existing 10,000-line cap and protected append behavior. No migration is needed beyond already-deployed `0010`. Remaining limits: a process killed before it can complete a journal write can leave incomplete spans; a complete D1 outage can also prevent server diagnostics. Notifications dismissed by the system/user before this app can observe them may still lack a receipt. View/callback/haptic-request records do not establish physical vibration, and cross-device clock offsets are not calibrated. The logger does not collect raw exceptions, SQL, bodies, tokens, addresses or credentials.

## Investigating an incident

1. Record approximate incident time/timezone and whether it involved detection, delivery, phone presentation or Watch presentation. Export iPhone diagnostics promptly from Settings → Diagnostics & simulation. For wrist-only symptoms inspect the Watch's Diagnostics screen too.
2. Find `network operation=... outcome=... request_id=...` around the failure. `transport_error` has a numeric URL error and often no response reference because no server response arrived. `decode_error` means an HTTP response arrived but did not match the app's expected data.
3. In Cloudflare's D1 console, query **only** diagnostic columns using the request UUID from the export:

   ```sql
   SELECT datetime(recorded_at/1000, 'unixepoch') AS utc,
          request_id, operation, stage, outcome, http_status,
          elapsed_ms, event_ref, attempt, target, release, details
   FROM diagnostics
   WHERE request_id = 'REPLACE-WITH-REQUEST-UUID'
   ORDER BY sequence;
   ```

4. For a dispatch row, query the same columns with `WHERE event_ref = 'REFERENCE-FROM-THAT-ROW' ORDER BY sequence` to follow cron retries. Do not query or share credentials/tokens/payloads. `release` identifies the Worker build to inspect; retain the matching source revision with deployment records.
5. Interpret the outcome:

   | Outcome | Meaning/action |
   | --- | --- |
   | `no_push_token`, `invalid_device_token` | Parent/Watch has no usable destination; check permission, signing/topic/environment and registration. |
   | `token_decryption` | Stored token cannot be decrypted with current configuration; inspect secret rotation/deployment, then re-register as appropriate. |
   | `provider_signing`, `provider_configuration`, `apns_environment` | Inspect APNs secret presence/format, key/team permissions, topic and development/production configuration without printing secrets. |
   | `apns_429`, `apns_500`, `apns_503` | Explicit retryable APNs response. Follow later attempts and cron health. |
   | `bad_topic`, `missing_topic`, `bad_priority`, `bad_expiration`, `bad_payload`, `payload_too_large`, `apns_rejected` | Explicit terminal rejection. Use the category, HTTP status and matching release to inspect payload construction. Unknown rejection text is deliberately discarded. |
   | `transport_unknown`, `dispatch_interrupted` | Acceptance is ambiguous. Check receiving devices; do not manually resend without evaluating duplicate risk. |
   | `sent` | APNs accepted the request. It does not prove phone/Watch display or haptic delivery. |
   | `internal_error` | Inspect operation/stage and matching release. Reproduce with synthetic data; raw production exceptions are deliberately not collected. |

6. Check cron liveness without reading functional metadata:

   ```sql
   SELECT datetime(MAX(recorded_at)/1000, 'unixepoch') AS last_success_utc
   FROM diagnostics WHERE operation = 'maintenance' AND outcome = 'ok';
   ```

   A missing or several-minutes-old result needs investigation. Check Cloudflare invocation/error metrics and configured cron trigger. Successful cron with no pending alerts still writes a completion row. `server_diagnostics=unavailable` in an app export signals missing journal evidence, not successful persistence.

## Remaining limits and operational work

- Deploy migration `0003_diagnostics.sql` before the updated Worker so diagnostic persistence is available. Rebuild/install both phone and Watch apps. These changes alone do not alter the live service.
- No automatic backend/cron outage notification or independent synthetic monitoring is configured. The optional Listener connection notices introduced in `0004_readiness.sql` require the backend and minute cron to remain healthy. Operators need a check for stale cron completion, elevated 503s, blocked/uncertain alerts and diagnostic storage failures. Do not point an unattended monitor at real child data; use a dedicated synthetic pair and define cleanup/notification ownership.
- The journal shares D1 with the application. A total D1 outage can prevent both application work and server diagnostic persistence. Client exports and Cloudflare aggregate metrics are the fallback. A killed Worker can leave no completion record; lease recovery records the affected dispatch on the next cron run.
- App logs cannot execute after a crash, force quit, watchdog kill or OS termination. Collect the matching iOS/watchOS crash, hang or jetsam report through Xcode/device diagnostics or Organizer, with user consent. Keep the exact release archive and dSYMs for symbolication. No crash/MetricKit upload SDK is installed by this change.
- Log sampling/caps intentionally trade exhaustive history for privacy, storage and performance. No source review can guarantee every future issue is diagnosable. Physical locked-screen, interruption, offline/reconnect, Focus/Silent Mode, wrist delivery and overnight checks still matter.
